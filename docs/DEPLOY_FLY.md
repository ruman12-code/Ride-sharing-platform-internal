# Putting Ekpothe on the internet

Everything here is yours to do — it needs accounts and a card, which I cannot
create. Budget an hour the first time. Steps 1 and 2 are the ones that block
everything else, so do them first even if you stop there for the day.

Fly.io was chosen for one reason that is not a preference: this app keeps its
data in a single SQLite file and runs a timer that closes out trips and sends
reconfirmations. Serverless hosts (Vercel, Netlify, Cloudflare Workers) give you
neither a disk that survives a deploy nor a process that stays alive between
requests. On one of those, the pilot would lose rides and bookings continuously.
Anything that runs an ordinary Node process with a persistent disk works —
Railway, Render, a $5 VPS — Fly is just the one these files are written for.

---

## 1. Email — do this first

Without a working mailer **nobody can sign in at all**, because the sign-in link
is the only door. This is the single hardest dependency in the app.

Full instructions are in `EMAIL_SETUP.md`. The short version: create a free
Brevo account (300 mails a day, far more than a pilot of twenty needs), verify
your sender address, and generate an SMTP key. You will end up with five values:
`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`.

Do not use your personal Gmail password. If you use Gmail at all, use an App
Password, and expect Google to be less reliable than Brevo for this.

## 2. Push keys

You already have these — they are in `.env.local`, generated by `npm run setup`.
Copy `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` out of that file. Do not
regenerate them once colleagues have subscribed: every existing subscription is
tied to the old key and would go silent.

## 3. Fly

```sh
# Install the CLI (macOS/Linux)
curl -L https://fly.io/install.sh | sh
fly auth signup      # or: fly auth login

cd Ride-sharing-platform-internal

# Create the app without deploying yet — the volume and secrets come first.
fly launch --no-deploy --name ekpothe --region sin --copy-config

# The disk. Without it the database lives inside the image and every deploy
# starts the pilot over from nothing.
fly volumes create data --size 1 --region sin

# Everything secret. These are never written into fly.toml, which is in git.
fly secrets set \
  ADMIN_EMAIL='ruman12@gmail.com' \
  APP_URL='https://ekpothe.fly.dev' \
  SMTP_HOST='smtp-relay.brevo.com' \
  SMTP_PORT='587' \
  SMTP_USER='...' \
  SMTP_PASS='...' \
  SMTP_FROM='Ekpothe <you@yourdomain>' \
  VAPID_PUBLIC_KEY='...' \
  VAPID_PRIVATE_KEY='...' \
  VAPID_SUBJECT='mailto:ruman12@gmail.com'

fly deploy
```

`sin` is Singapore, the closest region to Dhaka. Latency is not really the point
— a single machine is, so that one SQLite file has exactly one writer.

`APP_URL` matters more than it looks: it is what the sign-in links point at. Set
it to the address colleagues will actually open, and change it if you later put
a custom domain in front.

## 4. Check it before you tell anybody

```sh
fly logs          # you want: "push: on" and "email: relay reachable"
open https://ekpothe.fly.dev/api/health     # {"ok":true}
```

`fly logs` is where the honest answer lives. The server checks the SMTP
connection at boot and says so plainly. If it prints `email: BROKEN`, fix that
before going further — everything downstream of it is invisible failure.

Then, on your own phone:

1. Register with your personal address. You are approved immediately, because it
   matches `ADMIN_EMAIL`.
2. Ask for a sign-in link. It should arrive within a minute.
3. Tap it. You should land signed in.
4. Turn on notifications when the app offers.
5. Post a ride, then open the app in a private window as a second colleague and
   book it. You should get a notification without the app being open.

If step 2 produces nothing, it is email, not Fly. Check `fly logs`.

## 5. Every deploy after this

```sh
git push                 # to the branch
fly deploy               # from your machine
```

The database is on the volume and is not touched by a deploy.

## Backups

Do this once, and do it before you invite anybody. The whole pilot is one file.

```sh
fly ssh console -C "cat /data/carpool.db" > backup-$(date +%F).db
```

Run it weekly. It is not elegant, and it is enough: one bad restart without a
backup is the whole pilot, and a copy on your laptop is the difference between
an afternoon's annoyance and starting again.

## What is deliberately not here

**A custom domain.** `ekpothe.fly.dev` is free, has HTTPS, and works. A domain
is a nice-to-have you can add later with `fly certs add`; adding it on launch
day is one more thing to go wrong.

**A second machine.** SQLite has one writer. A second machine would be a second
process writing its own copy of the file on its own volume, and the two would
diverge silently — two colleagues seeing different rides, with nothing obviously
broken. If the pilot ever outgrows one machine, the storage has to change first.
For twenty people it will not come close.

**A staging environment.** For a pilot this size, `fly deploy` and `fly logs`
are the feedback loop.
